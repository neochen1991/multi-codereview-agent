# AI 代码检视工具开发同学使用培训

> 适用对象：日常提交 MR / PR 的开发同学、技术负责人、代码 Review 参与者。  
> 培训目标：会配置仓库、会发起一次检视、会看懂正式问题和关联影响分析、会处理人工确认、会把误报反馈沉淀为后续经验。

## 1. 这是什么工具

`multi-codereview-agent` 是一个面向 MR / PR 的 AI 代码检视工具。它会把一次代码变更交给多个检查角色协同审查，例如正确性、安全、数据库、性能、DDD、测试和通用代码质量等角色。

工具的目标不是替代开发同学做最终判断，而是帮助团队在合入前更早发现这些问题：

- 新代码引入的真实缺陷，例如金额计算错误、权限校验缺失、异常吞掉、事务边界错误。
- 影响范围扩大，例如一个方法签名变化影响调用方、测试覆盖不足、下游查询或缓存语义变化。
- 产品或团队自定义规则违规，例如订单导出字段必须脱敏、某类接口必须校验租户、某些状态流转必须经过审批。
- 需要人工确认的高风险争议点，例如证据不足但影响可能较大的问题。

一句话理解：它是一个“多专家 AI 预审 + 关联影响分析 + 人工反馈学习”的代码检视工作台。

## 3. 适合什么时候用

建议在这些场景使用：

- MR 已经完成自测，准备提交给同事 Review 前。
- 变更涉及核心业务、鉴权、金额、状态流转、数据库访问、缓存、消息、批处理、导出、定时任务。
- MR 文件较多，人工很难快速判断影响范围。
- 需要检查变更是否违反团队产品规则或代码规范。
- 想把人工驳回、人工确认的问题沉淀成后续检视经验。

不建议把它用于：

- 还没有编译通过的半成品代码。
- 没有明确 diff 的大段历史代码扫描。
- 纯格式化、纯注释调整且风险很低的变更。
- 直接代替开发本人理解业务影响。

## 4. 工具整体流程

一次检视大致会经历这些阶段：

1. **读取 MR 信息**  
   工具读取 MR 的 diff、目标分支、本地代码仓配置和已保存的代码仓设置。

2. **准备合入后代码快照**  
   如果开启实时快照能力，工具会尝试构造 MR 合入目标分支后的 worktree。这样 GitNexus 和 Tree-sitter 分析的是“新代码”，不是本地旧 dev 分支。

3. **关联上下文分析**  
   工具优先使用 Tree-sitter 图谱寻找调用方、被调方、接口实现、测试影响和最小上下文；没有命中时退化到关键词搜索。  
   如果启用 GitNexus，会生成更偏“影响范围和调用链”的分析报告。

4. **主 Agent 分派检查角色**  
   主 Agent 根据变更内容选择相关检查角色，例如安全专家、数据库专家、正确性专家等。

5. **专家 Agent 检视**  
   每个检查角色会读取：
   - 当前 MR diff
   - 合入后当前代码片段
   - Tree-sitter / GitNexus / 关键词检索到的关联上下文
   - 专家通用规范
   - 语言和框架通用规范
   - 附加产品/仓库规则
   - 历史人工反馈学习样本

6. **结果治理和去误报**  
   系统会过滤旧代码问题、行号不在 diff 中的问题、证据不足的问题、人工已驳回过的类似误报。

7. **输出结果和影响分析**  
   最终在结果页展示正式问题、证据链、建议修复、调用链图、关联影响分析、人工确认项和质量治理信息。

## 5. 首次使用前要确认什么

开发同学通常不需要自己部署工具，但第一次使用前建议确认这些事：

- 后端和前端已启动。
- 设置页里已经配置了目标代码仓。
- 目标代码仓路径正确，默认分支正确。
- 模型配置可用，工具能正常调用 LLM。
- 如果需要关联影响分析，GitNexus 状态正常。
- 如果是 Java 项目，Tree-sitter 图谱已建立或允许检视时实时构建。

常用访问地址：

- 前端：`http://127.0.0.1:5174`
- 后端健康检查：`http://127.0.0.1:8011/health`

如果是 Windows 环境，建议优先用项目提供的一键启动脚本：

```bat
scripts\start-all.bat
```

macOS / Linux：

```bash
bash scripts/start-all.sh
```

## 6. 5 分钟快速跑通

如果环境已经由负责人配置好，可以按这个最短路径跑一遍：

1. 打开 `http://127.0.0.1:5174`。
2. 进入 **设置**，确认目标代码仓、模型、GitNexus、Tree-sitter 状态不是异常。
3. 进入 **检视工作台**，填写 MR 信息或选择已有 MR。
4. 保持默认检查角色，点击开始检视。
5. 在 **过程记录** 中确认出现模型调用、检查角色分派、Tree-sitter 或关键词上下文记录。
6. 等待结果生成后，先看 **审核发现清单** 和 **正式问题**。
7. 对真实问题进行修复；对明显误报进行人工驳回并写明原因。

第一次培训时，建议先用准备好的示例 MR，不要直接用复杂线上大 MR。

## 7. 设置页怎么配

进入 **设置页** 后重点看这些区域。

### 7.1 代码仓配置

当前工具以“多代码仓设置”为主。每个代码仓至少要配置：

- 仓库标识
- 本地代码仓路径
- 默认分支
- Git 访问凭据或本地可访问路径

注意：

- 本地代码仓必须能正常执行 `git status`。
- 默认分支要和 MR 的目标分支一致或可对应。
- 多仓项目要把相关仓库都加进去，工具会按配置集合查找。

### 7.2 GitNexus

GitNexus 是可选增强能力，主要用于关联影响分析和调用链影响判断。

使用建议：

- 普通小 MR 可以不开启实时 GitNexus。
- 核心链路、大范围重构、接口变更、基础组件变更建议开启。
- 大仓库或 Windows 机器上，建图耗时可能较长，需要耐心等待。

如果设置页显示 GitNexus 不可用，先在命令行确认：

```bash
gitnexus list
gitnexus status
```

Windows PowerShell 同理：

```powershell
gitnexus list
gitnexus status
```

### 7.3 Tree-sitter 代码图谱

Tree-sitter 用来做本地代码结构解析，尤其对 Java 项目有价值。

它能帮助工具找到：

- 当前改动方法属于哪个类。
- 方法的调用方和被调方。
- 接口和实现类关系。
- 可能受影响的测试。
- 最小必要上下文，而不是把整个类丢给 LLM。

设置页里可以点击“建立/刷新图谱”。成功后通常会在代码仓下生成：

```text
<repo>/.code-review-graph/graph.db
```

### 7.4 实时 MR 快照开关

设置页中有实时快照相关开关。它决定 GitNexus 和 Tree-sitter 分析哪份代码。

- 关闭时：使用设置页配置的本地代码仓和已有图谱，速度更快，适合普通小 MR。
- 开启时：工具会尝试构造本次 MR 合入目标分支后的 worktree，并在快照上构建或刷新图谱，适合核心链路、大重构、接口变更。

如果 MR 的 source/head 无法被拉取，工具可能只能基于 diff 做降级分析。此时过程记录会显示降级原因。

## 8. 如何发起一次 MR 检视

一般操作步骤：

1. 打开工具首页。
2. 进入新建检视入口。
3. 填写或选择 MR 信息。
4. 确认代码仓、源分支、目标分支、MR diff。
5. 选择检视模式。
6. 提交任务。
7. 进入过程记录页观察执行进度。

如果你只是想快速跑一遍，通常保持默认配置即可。  
如果这次 MR 风险较高，建议启用：

- Tree-sitter 图谱上下文
- GitNexus 关联影响分析
- 实时 MR 合入快照

## 9. 过程记录页怎么看

过程记录页不是简单日志，它能帮助你判断工具有没有真的按预期检视。

重点看这些信息：

- **主 Agent 分派**：选了哪些检查角色，为什么选。
- **规则筛选**：命中了哪些附加产品/仓库规则。
- **Tree-sitter 调用记录**：是否使用结构化代码图谱，取到了哪些调用方、被调方、实现类、测试。
- **GitNexus 调用记录**：是否完成图谱分析，是否生成影响范围。
- **专家输出**：每个检查角色给出了哪些发现。
- **过滤和降级记录**：哪些问题因为旧代码、证据不足、规则引用不合法等原因被丢弃或降级。

如果你看到过程记录里只有很少的上下文，或者 Tree-sitter / GitNexus 一直不可用，检视质量通常会下降。

## 10. 结果页怎么看

结果页最重要的是 **审核发现清单**。开发同学建议按这个顺序看。

### 10.1 先看正式问题

优先处理：

- `blocker`
- `high`
- 明确标记为 `direct_defect`
- 证据链完整的问题
- 命中产品规则的问题

暂缓处理：

- 置信度低的问题
- `verification_needed=true` 的待验证风险
- 只有推断、缺少直接代码证据的问题

### 10.2 看问题详情

一个合格的问题详情应包含：

- 问题主张：到底哪里错了。
- 当前代码定位：应该定位到 MR 新代码的具体行，而不是整类代码或旧代码。
- 证据：至少能看到 diff 证据或关联上下文证据。
- 规范与规则依据：
  - 专家通用规范
  - 语言/框架通用规范
  - 附加产品/仓库规则
- 修复建议：怎么改，最好有建议代码片段。
- 影响范围：调用链、受影响文件、测试缺口。

### 10.3 看关联影响分析

关联影响分析用来回答：

- 这个改动会影响谁。
- 哪些调用链会经过这里。
- 哪些测试可能需要补。
- 哪些上下游模块需要关注。

如果页面显示调用链图，优先看：

- 当前变更节点。
- 上游调用方。
- 下游依赖。
- 风险路径。
- 测试覆盖缺口。

### 10.4 看质量治理与仓库策略

这一块是补充信息，不是第一优先级。它主要告诉你：

- 哪些问题被过滤。
- 哪些问题因为证据不足被降级。
- 是否命中仓库策略。
- 是否受历史人工反馈影响。

## 11. 什么是附加产品/仓库规则

工具内置的专家通用规范一直生效，例如：

- 安全专家会看鉴权、越权、敏感信息、注入。
- 正确性专家会看金额、状态流转、边界条件、幂等。
- 性能专家会看循环调用、批量路径、超时、重试、资源耗尽。
- 数据库专家会看 SQL、索引、事务、查询语义。

附加产品/仓库规则是在此基础上的增强，不是唯一准入条件。

例如产品规则：

```text
ORDER-SEC-001：订单导出接口必须对手机号、身份证号、收货地址做脱敏。
```

如果 MR 新增：

```java
row.put("phone", user.getPhone());
row.put("address", order.getAddress());
```

工具应该同时说明：

- 这违反安全专家通用规范：敏感信息输出必须脱敏。
- 这命中附加产品规则：`ORDER-SEC-001`。

如果 MR 新增：

```java
log.info("export token={}", token);
```

即使没有产品规则命中，它仍然可以作为安全专家通用问题进入正式清单，因为访问令牌不应写入日志。

## 12. 如何编写附加规则文档

在知识库页面上传 Markdown 文档，并绑定到对应检查角色。

规则文档建议使用模板：

````md
## RULE: ORDER-SEC-001 订单导出敏感字段必须脱敏

### 元数据
- 触发关键词: export, phone, address, getPhone, getAddress
- 风险类型: sensitive_export

### 一级场景
订单

### 二级场景
导出

### 三级场景
敏感字段明文输出

### 描述
订单导出接口新增手机号、身份证号、收货地址等字段时，必须使用脱敏工具输出，不能直接写入原始字段。

### 问题代码示例
```java
row.put("phone", user.getPhone());
row.put("address", order.getAddress());
```

### 问题代码行
row.put("phone", user.getPhone());

### 误报代码
```java
row.put("phone", Masking.maskPhone(user.getPhone()));
```

### 语言
java

### 问题级别
P1
````

编写建议：

- 一个规则只描述一个问题，不要把多个业务约束混在一起。
- 规则 ID 要稳定，例如 `ORDER-SEC-001`。
- `问题代码示例` 和 `误报代码` 都要写，能明显减少误报。
- 触发关键词要覆盖代码里常见命名，例如 `phone`、`mobile`、`address`、`export`。
- 规则级别建议使用 `P0 / P1 / P2 / P3`。

## 13. 人工确认和反馈学习怎么用

有些问题工具会要求人工确认。开发同学需要做两类操作。

### 13.1 批准

如果问题确实存在，点击批准。系统会把它作为正例学习。

适合批准的情况：

- 问题定位准确。
- 代码证据充分。
- 修复建议方向正确。
- 问题确实由本次 MR 引入或暴露。

### 13.2 驳回

如果问题是误报，点击驳回并写清原因。系统会把它作为反例学习。

建议驳回理由写具体一些，例如：

```text
误报：该接口只由后台定时任务调用，不需要用户态租户校验；机器身份校验在 JobAuthInterceptor 中完成。
```

不要只写：

```text
不对。
```

好的驳回理由能帮助后续减少同类误报。

### 13.3 反馈学习会不会污染后续检视

反馈学习不会简单地把某条驳回记录原样塞进所有 prompt。更合理的使用方式是：

- 把人工批准的问题沉淀为正例，帮助系统识别同类真实缺陷。
- 把人工驳回的问题沉淀为反例，帮助系统降低相似误报的优先级。
- 只在相似文件、相似规则、相似代码形态下影响判断，避免把一个局部例外放大到全仓库。
- 仍然保留专家通用规范和产品规则作为主要判断依据。

所以驳回时一定要写清楚“为什么是误报”，尤其是业务前提、上游保障、已有拦截器、已有脱敏工具等信息。

## 14. Benchmark 评测中心怎么用

评测中心用于评估工具检视质量，不是日常每个 MR 都必须使用。

适合这些场景：

- 团队想验证工具是否能发现某类问题。
- 新增产品规则后，需要验证命中效果。
- 升级模型、prompt、Tree-sitter、GitNexus 后，需要对比质量。
- 培训时构造示例 MR 给大家演示。

评测时建议准备：

- 一个包含预埋问题的 MR。
- 预期应该发现的问题清单。
- 哪些问题属于误报。
- 哪些影响范围应该被识别。

评测结果重点看：

- 预埋问题命中率。
- 误报数量。
- 问题行定位是否准确。
- 关联影响分析是否覆盖调用方、被调方、测试缺口。
- 前端展示是否能让开发同学看懂。

## 15. 开发同学处理结果的建议

建议按这个流程处理：

1. 先看 `blocker/high` 正式问题。
2. 再看命中产品规则的问题。
3. 对每个问题确认：
   - 是否在 MR 新代码范围内。
   - 是否是新代码引入或暴露。
   - 证据是否充分。
   - 修复建议是否可执行。
4. 能确认的问题直接修。
5. 不确定的问题查看关联影响分析。
6. 明显误报就人工驳回，并写清原因。
7. 修改后重新跑一次检视或在 MR 中补充说明。

## 16. 常见问题

### 16.1 为什么有些问题没有进入正式清单

可能原因：

- 问题定位不在 MR 新代码行。
- LLM 提到了旧代码，系统识别为旧代码问题并丢弃。
- 证据不足，被降级为待验证观察。
- 与历史人工驳回样本相似，被反馈学习机制压低。
- 专家越界，例如安全问题被通用代码质量专家误报。

### 16.2 为什么没有命中产品规则，但仍然报了问题

这是正常的。产品规则是附加规则，不是唯一准入条件。专家通用规范和语言/框架通用规范一直生效。

例如：

- `token` 写入日志。
- SQL 拼接注入。
- 金额计算公式错误。
- `Optional.get()` 无保护。
- 循环内远程调用。

这些即使没有产品规则，也可以成为正式问题。

### 16.3 为什么命中了产品规则，但没有报问题

规则命中只是“必须检查”，不是“一定有问题”。如果代码已经满足规则，工具可以不报。

例如产品规则要求手机号脱敏，而代码已经是：

```java
row.put("phone", Masking.maskPhone(user.getPhone()));
```

这就不应该报。

### 16.4 为什么有时关联影响分析比较慢

GitNexus 和 Tree-sitter 都需要读取代码仓并构建图谱。大仓库、Windows 机器、首次建图、MR 文件较多时会更慢。

建议：

- 设置页提前为常用仓库建图。
- 大 MR 开启实时快照时预留更多时间。
- 如果只是小变更，可以关闭实时 GitNexus。

### 16.5 结果里出现英文怎么办

面向用户的说明字段应该尽量是中文。少量字段如 `normalized_issue_type`、类名、方法名、规则 ID 是英文属于正常。如果修复建议、证据说明出现大段英文，可以作为产品问题反馈。

### 16.6 为什么工具报了旧代码问题

正式问题应该优先锚定 MR 新增或修改后的代码。如果发现问题详情展示的是旧代码、待删除代码，或者当前代码定位不准确，可以这样处理：

- 先检查问题详情里的文件和行号是否在本次 MR diff 中。
- 再看当前代码片段是否为合入后的新代码。
- 如果明显不是本次 MR 引入，人工驳回并说明“旧代码问题/非本次变更”。
- 如果是因为 diff 或快照信息缺失导致定位错误，将 review_id、文件路径、问题 ID 反馈给工具维护同学。

## 17. 培训演练建议

建议培训时用 45 分钟走一遍。

### 17.1 10 分钟：工具定位

讲清楚：

- 它不是替代人工 Review。
- 它适合做合入前预审。
- 它能帮助发现问题、补充影响分析、沉淀反馈学习。

### 17.2 15 分钟：跑一个 MR

准备一个 Java MR，包含：

- 一个通用安全问题：`token` 写日志。
- 一个产品规则问题：订单导出手机号明文。
- 一个误报保护场景：已经脱敏的手机号不应报。

演示：

- 新建检视。
- 过程记录页看专家、规则、Tree-sitter。
- 结果页看正式问题和影响分析。

### 17.3 10 分钟：处理结果

演示：

- 批准真实问题。
- 驳回误报。
- 查看问题详情里的证据链。
- 查看规范与规则依据。

### 17.4 10 分钟：新增产品规则

演示：

- 在知识库上传 Markdown 规则。
- 绑定到对应检查角色。
- 重新跑检视。
- 对比规则命中和结果变化。

## 18. 合并前检查清单

在把 AI 检视结果作为 MR 依据前，建议开发同学快速确认：

- 本次检视使用的是正确代码仓和正确目标分支。
- 过程记录里有 LLM 调用记录，不是只跑了本地兜底。
- 对 Java MR，Tree-sitter 或关键词上下文至少有一种成功返回。
- 如果开启 GitNexus，影响分析没有显示关键错误或超时未降级说明。
- 正式问题的代码定位在本次 MR 新代码范围内。
- 高优先级问题都有明确证据、规范依据或产品规则依据。
- 人工驳回的问题已经写清楚驳回原因。
- 修复后已经重新运行检视，或在 MR 评论里解释未重新运行的原因。

## 19. 开发同学使用守则

- 不要把 AI 结论直接当最终结论，必须结合业务和代码判断。
- 优先处理证据明确、行号准确、影响范围清楚的问题。
- 看到误报要驳回并写清原因，帮助工具学习。
- 产品规则要写成小而明确的规则卡，不要写成长篇制度文。
- 大 MR 建议拆小，否则影响分析和结果阅读都会变难。
- 对核心链路变更，建议保留检视报告作为 MR 附件或评论依据。

## 20. 一句话总结

这个工具的正确使用方式是：开发同学先自测，再用 AI 多专家预审找缺陷和影响范围，最后由人确认、修复和反馈。工具越能拿到准确 diff、当前代码、关联上下文和清晰产品规则，检视质量就越高。
